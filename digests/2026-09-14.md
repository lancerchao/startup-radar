## Ideas

Three candidates this cycle, all rejected — the forty-first straight cycle with zero survivors.

### 1. Fitbit Web API → Google Health API migration tooling for third-party developers — REJECTED (new)

- **Brief description:** A drop-in compatibility layer for third-party fitness/health apps still calling the legacy Fitbit Web API — handling OAuth re-consent, user-ID remapping, and data-model translation to the new Google Health API ahead of this month's shutdown.
- **Risks:** The buyer segment (developers still calling Fitbit's API directly, having ignored months of deprecation notices) is small and shrinking to zero the moment the cutoff hits.
- **Consumer/buyer pain (quantified):** Real and forced — existing OAuth tokens don't carry over, so every end-user must explicitly re-consent through Google OAuth or their data silently stops syncing; new Fitbit developer registrations are already closed, so no new entrants can even join the affected pool.
- **Why now, not 2 years ago:** Genuinely dated — the legacy API is being decommissioned this month.
- **Why don't existing big players compete — they already ship the fix:** Google's own developer site provides a comparison tool, an API Explorer, and a user-linking API that maps legacy Fitbit user IDs to new Google Health IDs specifically to smooth this transition.
- **Why isn't it saturated yet — it is, from both the paid and free side:** A cluster of funded wearable-data aggregators already sell "connect once, we abstract every wearable including this exact migration" as their core pitch — Sahha ($4M raised total, ~300 device/app integrations, per-user SaaS pricing) plus Terra API, Rook, Thryve, Junction, and Spike compete in the identical category. Below them, Open Wearables (built by digital-health agency Momentum) ships a free, MIT-licensed, self-hosted version with a documented Fitbit-to-Health-API migration path.
- **What will change in the next 2 years:** More wearables (Whoop, Oura, Garmin) get pulled into the same aggregator layer as the industry consolidates around unified wearable-data APIs — reinforcing the aggregators' position, not opening room for a Fitbit-specific bridge.
- **Competitors:** Sahha, Terra API, Rook, Thryve, Junction, Spike (funded aggregators); Open Wearables (free, open-source); Google's own official migration tooling.
- **Who pays / sales motion:** Would be developer-tool self-serve SaaS, but the affected buyer pool is a sliver that's actively shrinking as the deadline passes.
- **Expected CAC / LTV / ARR ceiling:** Not meaningfully scoreable — the buyer this idea needs almost doesn't exist by the time it could ship.
- **Time to first sellable version / Operational load:** An OAuth-handling wrapper could ship in days, which is exactly why six better-resourced competitors already ship the fuller version as one integration among hundreds.
- **Sources:** [Sahha — Fitbit sunset migration](https://sahha.ai/blog/fitbit-api-sunset-migration/), [Sahha funding — Fitt Insider](https://insider.fitt.co/press-release/sahha-ai-raises-1-2m-to-scale-their-health-wearable-data-engagement-api/), [Open Wearables (GitHub)](https://github.com/the-momentum/open-wearables), [Momentum — Fitbit deprecation guide](https://www.themomentum.ai/blog/fitbit-web-api-deprecation-google-health-migration), [Fitbit official migration guide](https://dev.fitbit.com/build/guides/migration/).
- **Kill reason:** Google ships the official migration path directly, and the rational move for an affected developer — switch to a wearable-data aggregator that already abstracts Fitbit away entirely — is already served by six named companies, one free and five funded. Sixth confirmed instance of this ledger's "vendor API sunset → migration tool" shape (after Assistants API, Stocky, MTurk, Notion Mail, and PAT-to-GitHub-App).
- **Not scored against B2C_RULES** — B2B, buyer is an app developer.

### 2. Sora 2 API shutdown (Sept 24, 2026) migration/routing layer — REJECTED (new, brief pass)

- **Brief description:** A compatibility/routing layer letting apps built on OpenAI's Sora 2 video-generation API redirect calls to alternative models (Veo 3.1, Kling, Runway) ahead of the September 24, 2026 hard cutoff.
- **Why isn't it saturated — it is, with the longest runway of any instance on this ledger:** OpenAI gave developers the deprecation notice on March 24, 2026 — six months' notice, longer than the Assistants API, Stocky, MTurk, or Notion Mail shutdowns that preceded it on this ledger — and at least 8 named publishers (Spheron, OpusClip, Rangy, Seedance2, MichyDev, ai-tldr, Pixo, apiyi) already have live Sora-alternative and migration content, with Pixo specifically offering a multi-model routing interface (Sora, Seedance, Kling, Veo, Wan in one API) that is the exact product this idea would build.
- **Kill reason:** Seventh confirmed instance of this ledger's "vendor API sunset → migration tool" shape, and the one with the most advance notice yet — which gave incumbents more time to cover it, not less.
- **Sources:** [apiyi — Sora 2 API shutdown & alternatives](https://help.apiyi.com/en/sora-2-api-shutdown-alternatives-2026-en.html), [Spheron — self-hosted video alternatives](https://www.spheron.network/blog/sora-2-api-shutdown-2026-self-hosted-video-alternatives/), [Rangy — What Happened to Sora](https://rangy.ai/blog/what-happened-to-sora/), [Pixo — Sora API still available](https://pixo.video/blog/sora-api-still-available).
- **Not scored against B2C_RULES** — B2B/developer tool; killed on Rule 9 (over-mined shape) before a full deep-dive was warranted.

### 3. Software-only mobile driver's license (mDL) age-verification for small retailers — REJECTED (new)

- **Brief description:** A phone-camera/browser-based subscription tool (no proprietary hardware) letting small single-location bars, breweries, vape shops, and dispensaries verify a customer's mobile driver's license from Apple/Google/Samsung Wallet at checkout, riding the accelerating US mDL rollout.
- **Risks:** The exact software-only mechanism this idea needs is already live, free, and open-source.
- **Consumer/buyer pain (quantified):** Real and growing market — global mobile identification market projected to grow from $13.94B (2025) to $15.77B (2026), 13.1% CAGR; Apple Wallet ID expanded to 4 more US states in August 2026 alone; North Carolina plans a statewide mDL rollout for December 2026; TSA accepts mobile IDs at a growing number of checkpoints.
- **Why now, not 2 years ago:** mDL crossed from pilot to mainstream only this year (22+ US states/territories live), and the browser-side standards needed for camera/browser-only verification (Web Bluetooth, the Digital Credentials API) only matured enough for production use in 2026.
- **Why don't existing big players compete — they already ship this, free:** Stelau's mDoc Web Verifier is a free, open-source (MIT), zero-signup, fully client-side ISO 18013-5 reader/verifier that runs in any browser with no server or account, and already supports mDL, EU digital ID, and dedicated age-verification credential types.
- **Why isn't it saturated yet — it is, on every segment:** Hardware-forward vendors (CredenceID's Tap2iD terminal, Scytáles' validator SDK) already serve larger/multi-location retailers; free options (Stelau's browser verifier, the "Check ID" free ID-scanner app) already serve the exact solo/single-location buyer this idea targets, at zero switching cost.
- **What will change in the next 2 years:** More states and wallets get added to mDL support, and more retail categories accept it — but each is a checkbox added to tools already live and free today, not a new opening.
- **Competitors:** Stelau (free, open-source), Check ID (free app), CredenceID, Scytáles, plus incumbent physical ID-scanner vendors (BottlePOS, IDScanner.com/AgeVisor) already selling into the identical small-retailer buyer.
- **Who pays / sales motion:** Would be self-serve SaaS to small retailers, but a free tier already fully replicates the core verification mechanism.
- **Expected CAC / LTV / ARR ceiling:** Not meaningfully scoreable — no gap between the free tier and the enterprise-hardware tier for a new paid entrant to occupy.
- **Time to first sellable version / Operational load:** A wrapper around the existing open-source verifier could ship in days — which is exactly why it's already live, free, and open-source today.
- **Sources:** [Stelau mDoc Web Verifier](https://mdoc-web-verifier.stelau.com/), [Stelau verifier (GitHub)](https://github.com/stelauconseil/mdoc-web-verifier), [Biometric Update — US mDL ecosystem](https://www.biometricupdate.com/202609/us-mdl-ecosystem-grows-as-states-add-wallets-tsa-support), [Research and Markets — mobile ID market](https://www.researchandmarkets.com/reports/6177694/mobile-identification-market-report), [Talking Retail — UK digital ID age-restricted sales](https://www.talkingretail.com/news/industry-news/acs-welcomes-progress-on-digital-id-adoption-for-age-restricted-sales-01-07-2026/).
- **Kill reason:** The exact software-only, no-hardware mechanism this idea would build is already live, free, and open-source (Stelau's browser-based mDL verifier), with hardware vendors covering the multi-location tier above it and free ID-scanner apps covering the solo-retailer tier below — no seam left for a paid new entrant.
- **Not scored against B2C_RULES** — B2B, buyer is a small retailer, not a consumer.

**Bottom line:** Forty-first straight cycle, zero survivors. Two of three candidates this cycle were fresh instances of this ledger's most over-mined shape — "a vendor sunsets an API/platform, build the migration tool" — now confirmed a sixth and seventh time across two completely different domains (wearable health data, AI video generation), always killed the same way: either the vendor ships official migration tooling itself, or better-resourced incumbents (funded aggregators, multi-model routing platforms) already abstract the dependency away before a solo founder could ship. The third candidate names a new pattern worth watching: for anything shaped like "verify a credential against a physical-world rule" (age verification, identity checks), assume a free, open-source, browser-based tool already exists before spending research time on a paid version — the same absorption dynamic as the regulation-to-compliance-tool tarpit, one layer down at the verification-mechanism level.
